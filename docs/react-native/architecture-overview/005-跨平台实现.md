## 为什么需要跨平台共享实现

早期渲染系统在 Android 与 iOS 分别实现 Shadow Tree、布局逻辑和 View Flattening。维护两份实现会增加修复和演进成本，也可能让相同 UI 在不同平台逐渐出现差异。

New Architecture 将更多渲染核心放进共享 **C++** 实现。这样不同宿主平台可以复用 React Shadow Tree、布局和视图差异计算等逻辑；共享实现也为后续接入 Windows、电视或游戏主机等宿主提供更统一的起点。

## 共享 C++ 核心的作用

- **减少重复维护**：核心渲染步骤在多个平台共享，修复可以应用于共同实现。
- **降低部分跨语言开销**：Android 上 Yoga 与 C++ renderer 的整合不再需要旧路径中的某些 JNI 调用。
- **减少节点内存占用**：C++ Shadow Node 的对象布局通常比在 Kotlin 或 Swift 层重复分配更紧凑。
- **支持并发安全**：不可变数据结构与 C++ 类型约束帮助多个线程安全地读取共享树状态。

这些优化减少特定路径的开销，但不表示 Android/iOS 之间完全没有语言边界调用。

## Android 仍有哪些 JNI 边界

**JNI（Java Native Interface）**是 Java/Kotlin 与 C/C++ 互相调用的接口。官方页面指出，Android renderer 仍会在一些场景跨 JNI：

1. 复杂视图（如 Text、TextInput）的布局测量需要把 props 交给宿主平台。
2. Mount 阶段需要把 view 的创建、插入、更新或删除操作应用到 Android host views。

页面提到团队在探索以 `ByteBuffer` 替换某些 `ReadableMap` 数据传递路径，并描述了降低 JNI 开销的目标。它属于技术演进方向，不应理解为所有 RN SDK 已经提供或保证了固定的性能提升。

## Renderer 两侧如何通信

Renderer 的 C++ API 面向两个方向：

| 方向 | 内容 | 举例 |
|---|---|---|
| React ↔ Renderer | 提交 React Tree，并订阅由视图产生的事件 | `onLayout`、键盘输入、触摸事件 |
| Renderer ↔ Host Platform | 在屏幕上管理宿主视图并接收用户操作 | 创建 / 插入 / 更新 / 删除原生视图 |

宿主平台（host platform）是实际运行 RN 的 Android、iOS 或其它目标系统；Host View 是由该系统绘制的原生视图。

## 关键名词

- **跨平台核心**：多个平台共享的一份内部实现，不表示所有 UI 代码都会在所有平台外观相同。
- **C++ Renderer**：React Native 用于构建和更新视图树的共享 C++ 渲染部分。
- **JNI**：Android Java/Kotlin 与 C/C++ 代码交互的机制。
- **Yoga**：React Native 使用的布局计算引擎。
- **ReadableMap**：旧式跨语言数据对象的接口之一，用于读取 JavaScript 传来的键值。
- **Host View**：最终由宿主平台绘制和操作的原生 UI 节点。
