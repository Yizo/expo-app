## 渲染流水线是什么

New Architecture 的 **render pipeline（渲染流水线）**是把 React 组件描述转成屏幕原生视图的一组阶段。可以先记住这条顺序：

```text
React 组件 / React Element Tree
        ↓ Render
React Shadow Tree（C++）
        ↓ Commit：计算布局并选定下一棵树
带布局数据的 Shadow Tree
        ↓ Mount：计算差异并更新宿主视图
iOS / Android Host View Tree
```

一次冷启动的首次渲染和后续状态更新都会经过这些阶段，但更新时会尽量复用没有变化的树节点。

## 首次渲染：Render

React 先执行 JavaScript 组件，得到 **React Element Tree**。`MyComponent` 属于由开发者编写的 Composite Component；真正对应平台 UI 的 `<View>`、`<Text>` 是 Host Component。Renderer 为 Host Component 创建 C++ **Shadow Node（影子节点）**，它保存布局、props 和树关系等描述。

```tsx
import { Text, View } from 'react-native';

function GreetingCard() {
  return (
    <View>
      <Text>你好，React Native</Text>
    </View>
  );
}
```

这段组件树可概念化为：`GreetingCard` → `View` → `Text`。`GreetingCard` 本身不会变成原生 View；里面的 Host Component 才进入 Shadow Tree。

## Commit：布局计算并确定下一棵树

当 Shadow Tree 完整后，Renderer 进入 **Commit（提交）**阶段。React Native 使用 **Yoga** 根据样式和根节点的可用宽高计算每个 Shadow Node 的位置与尺寸。接着执行 Tree Promotion，把这棵带有最新数据的树标记为待挂载的 **Next Tree**。

许多计算可以在后台线程完成；依赖平台字体或原生测量的组件（例如 Text / TextInput）还会请求宿主平台提供尺寸。提交阶段不是简单把 DOM 字符串发送给手机，而是在为原生视图准备结构化数据和布局结果。

## Mount：把树变化应用到原生界面

**Mount（挂载）**阶段会把 Shadow Tree 转成 **Host View Tree（宿主视图树）**。Android 上 `<View>`、`<Text>` 会落到 Android 视图；iOS 上会映射到 UIKit 视图。Mount 先比较上一棵屏幕树和 Next Tree，生成 create/update/remove 等原子操作，再在 UI thread 应用。

**Tree Diffing（树差异计算）**能避免整屏重建：若只有一个文字或颜色 prop 改变，Renderer 通常只更新受影响的宿主视图。View Flattening 还可能把只负责布局、没有独立绘制内容的节点合并，减少实际原生视图数量。

## 状态更新：不可变树与结构共享

假设初始 UI 有两个色块，之后只把第一个从红色改为黄色：

```tsx
import { useState } from 'react';
import { Button, View } from 'react-native';

function ColorTiles({ firstColor }: { firstColor: string }) {
  return (
    <View>
      <View style={{ width: 20, height: 20, backgroundColor: firstColor }} />
      <View style={{ width: 20, height: 20, backgroundColor: 'blue' }} />
    </View>
  );
}

function ColorTileDemo() {
  const [firstColor, setFirstColor] = useState('red');

  return (
    <>
      <Button title="把第一块改成黄色" onPress={() => setFirstColor('yellow')} />
      <ColorTiles firstColor={firstColor} />
    </>
  );
}
```

Renderer 不直接改写屏幕正在使用的 Shadow Tree，而是创建新的受影响节点及其祖先路径，再复用未改变的第二个色块节点。这种 **immutability（不可变性）**保护不同线程读取树时的数据一致性；**structural sharing（结构共享）**降低复制和内存开销。提交完成后，Mount 对比两棵树，只把第一块的背景色更新为黄色。

## C++ State 更新路径

大多数 React state 由 JS 维护，是 UI 的唯一数据源。有少数宿主组件需要保存不直接暴露给 JS 的状态，例如 `ScrollView` 当前滚动偏移；这类值可保存在 **C++ State**。

C++ State 变化不需要重新执行 JS Render 阶段，但仍需 Commit 和 Mount 来保持 Shadow Tree 与宿主视图一致。它可能从原生线程发起；如果期间另一个更新已提交，Renderer 会基于最新节点重试，避免两个来源覆盖彼此的状态。

| 类型 | 常见来源 | 是否经过 React Render | 例子 |
|---|---|---:|---|
| React State | JS 组件的 `useState` | 是 | 用户操作后更新组件内容 |
| C++ State | Host Component / 原生平台 | 否 | ScrollView 的原生滚动位置 |

## 关键名词

- **React Element Tree**：JS 组件执行后产生的 UI 描述树。
- **React Shadow Tree**：Renderer 在 C++ 侧构建的布局和原生 UI 描述树。
- **Host View Tree**：最终由 Android / iOS 原生 View 实例组成、可以显示到屏幕的视图树。
- **Yoga**：React Native 的跨平台布局引擎，负责依据 Flexbox 等样式计算位置和尺寸。
- **UI thread**：宿主平台处理界面视图更新的线程；重操作阻塞它会导致界面卡顿。
- **Tree Promotion**：将已准备好的新树标为下一棵待挂载树，保证后续更新针对一致版本进行。
