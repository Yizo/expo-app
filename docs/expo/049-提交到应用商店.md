## Build 和 Submit 的区别

Build 会生成已签名的 Android / iOS 二进制文件；Submit 会把二进制上传至 Google Play Console 或 App Store Connect。上传完成后仍要在商店配置上架信息、选择测试轨道并等待商店审核。

EAS Submit 通常是推荐路径，可在 macOS / Windows / Linux 上调用，也可接入 EAS Build / Workflows / CI。另一种方式是用商店自己的网页或 Xcode 手工上传。

## Google Play

EAS Submit 将 Android AAB 上传到 Play Console 指定轨道（Internal、Alpha、Beta 或 Production）。新 app 默认创建 Internal Testing release；要向更大范围测试者分发，需先完成 Play Console 项目设置，再把 release 推至目标轨道。

如只想上传二进制但暂时不推出到测试轨道，可在 eas.json 设置 releaseStatus 为 draft。

## Apple App Store / TestFlight

EAS Submit 将 iOS IPA 上传到 App Store Connect。处理完成后会出现在 TestFlight；这不等于自动正式发布。要上生产版，还需在 App Store Connect 完善元数据和截图、选定 build 并送交 App Review。

## 提交已有本地构建

EAS Submit 不要求 binary 一定由 EAS Build 生成；它接受已正确签名的 .aab 和 .ipa。指定本地文件：

~~~sh
eas submit --platform android --path ./my-app.aab
eas submit --platform ios --path ./my-app.ipa
~~~

Android 需要上传 keystore；iOS 需要 distribution certificate 与 provisioning profile。对于 EAS Build 产物，也可运行 eas submit 并从列表选构建，或使用最新构建。

## 自动化提交

EAS Workflows 可以让 submit job 依赖前面的 build job，再把生成的 build_id 作为输入：

~~~yaml
jobs:
  submit_ios_to_store:
    type: submit
    needs: [build_ios]
    params:
      build_id: ${{ needs.build_ios.outputs.build_id }}
~~~

CI 环境可通过 --non-interactive 跳过交互提示，通过 --latest 自动选择最新构建：

~~~sh
eas submit --platform android --latest --non-interactive
~~~

## 失败排查和职责边界

提交失败时先查看 EAS Dashboard 的 submission details 和日志；日志中的 Build Annotations 会标出常见原因。EAS Submit 只负责上传二进制，不维护应用商店的商家资料、截图或发布说明。

- Google Play 商店资料在 Play Console 编辑。
- Apple App Store 元数据可手动管理，也可用后续页介绍的 EAS Metadata。

## 关键名词

- **Submit**：将签名构建上传到 App Store Connect / Google Play Console 的过程。
- **Internal / Beta / Production track**：Play Console 的不同测试与发布轨道。
- **TestFlight**：Apple 的测试分发系统；出现 TestFlight 不代表 app 已正式上架。
- **AAB / IPA**：分别是 Android / iOS 的商店二进制格式。
- **Store metadata**：商店展示用的名称、描述、关键词、截图等信息，EAS Submit 本身不负责管理。
