## 先选择 Web 输出模式

Expo Router 的 app config 字段 web.output 决定导出的目录结构：

| 输出模式 | 产物 | 路由 / API 差异 |
| --- | --- | --- |
| single（默认） | dist 下一个 index.html | SPA；没有每条路径独立 HTML，也不会自动输出 API routes。 |
| server | server 和 client 输出目录 | client 为各路由输出独立 HTML；server 输出 API route JavaScript，交给自托管 Node server。 |
| static | 每个 app route 输出独立 HTML 文件 | 便于静态服务器 / SEO；API routes 需额外启用。 |

Latest Guide 的提示：SDK58 起可以在 expo-router config plugin 中设置 apiRoutes: true 来启用 static + API routes；server 输出默认启用 API routes，apiRoutes: false 可关闭。这个选项是 SDK58+，本地 SDK56 不应照抄。

app.json 可用 metro bundler 并选择 server output，例如：

```json
{
  "expo": {
    "web": {
      "output": "server",
      "bundler": "metro"
    }
  }
}
```

static 和 server 模式还可在 expo-router plugin 中配置全局 HTTP headers；具体 Hosting provider 的 header 规则需按目标服务器设置。

## 导出产物并本地预览

部署前先将 JavaScript 和 assets 编译到 dist。源页支持的包管理器命令：

```sh
npx expo export -p web
yarn expo export -p web
pnpm expo export -p web
bun expo export -p web
```

Expo export 生成的文件位于 dist；public 文件也会复制到 dist。Metro 保留少数特殊资源路径，例如 /assets，避免把自定义 public 文件放入这类保留目录。

导出完成后可用 Expo CLI 模拟静态 Hosting：

```sh
npx expo serve
yarn expo serve
pnpm expo serve
bun expo serve
```

然后访问 http://localhost:8081 检查导出的页面。该本地 server 使用 HTTP 而非 HTTPS；摄像头、定位等要求 secure context 的浏览器 API 可能因此无法按生产站点表现。

## EAS Hosting

Expo 官方推荐 EAS Hosting 作为默认方案，支持 custom domain、SSL 和与 Expo Router / Web API routes 一体的部署。其部署命令与环境配置在独立 EAS Hosting 指南中，本模块只在此记录它是首选部署入口，不执行任何线上部署。

## Netlify

Netlify 可以托管静态 dist 目录。使用 SPA 单文件输出时，为未知路径加 redirect 到 index.html；如果应用用了每页静态渲染，则跳过这个通配 redirect：

```text
/*    /index.html   200
```

文件应放到 public/_redirects；修改后再导出，文件才会复制进 dist。按包管理器安装 Netlify CLI 并手动上传 dist：

```sh
npm install --global netlify-cli
yarn global add netlify-cli
pnpm add --global netlify-cli
bun add --global netlify-cli

netlify deploy --dir dist
```

也可以把 Git repository 接入 Netlify，让 push / pull request 自动执行其 build and deploy。源页建议用其 Web console 完成连接。

## Vercel

Vercel 示例以 CLI 发布单文件 SPA：安装 CLI，然后在项目根目录创建 vercel.json：

```sh
npm install --global vercel@latest
yarn global add vercel@latest
pnpm add --global vercel@latest
bun add --global vercel@latest
```

```json
{
  "buildCommand": "expo export -p web",
  "outputDirectory": "dist",
  "devCommand": "expo",
  "cleanUrls": true,
  "framework": null,
  "rewrites": [
    {
      "source": "/:path*",
      "destination": "/"
    }
  ]
}
```

static rendering 下需要按 dynamic route 增加对应的 fallback / route 配置；完成项目配置后可由 CLI 部署：

```sh
vercel
```

## AWS Amplify Console

Amplify 的模式是从 Git repository 自动构建、托管 Expo Web 项目。源页链接了根目录所需的 amplify.yml 模板；步骤重点是：确保 build artifact dist 不在仓库忽略规则中、将模板放到 repository root、选择 Git hosting repository 和 branch，然后在 Console 里指定 app 的 dist path 并开启自动部署。Amplify 也可配置自定义域名和 SSL。

这段指南描述仓库 / Console 操作，没有在 Expo 页面内展示完整 YAML；要逐行配置需遵循 Expo 原始页面链接的 amplify.yml。

## Firebase Hosting

Firebase CLI 先创建 / 选择 Firebase project，再完成认证和 Hosting 初始化：

```sh
firebase login
firebase init
```

firebase init 的 public path 设为 dist。只有 web.output 是 single SPA 时才选择 rewrite 所有路径到 /index.html；static 输出有每个路由的 HTML，不使用该全站 SPA rewrite。

在 package.json 的 scripts 加 predeploy 和 deploy-hosting：

```json
{
  "scripts": {
    "predeploy": "expo export -p web",
    "deploy-hosting": "npm run predeploy && firebase deploy --only hosting"
  }
}
```

部署命令的包管理器形式：

```sh
npm run deploy-hosting
yarn run deploy-hosting
pnpm run deploy-hosting
bun run deploy-hosting
```

需要自定义 Cache-Control 时，firebase.json hosting headers 可令 HTML 每次重新验证，而图片 / 字体 / js / css 缓存 7 天：

```json
{
  "hosting": [
    {
      "headers": [
        {
          "source": "/**",
          "headers": [
            { "key": "Cache-Control", "value": "no-cache, no-store, must-revalidate" }
          ]
        },
        {
          "source": "**/*.@(jpg|jpeg|gif|png|svg|webp|js|css|eot|otf|ttf|ttc|woff|woff2|font.css)",
          "headers": [
            { "key": "Cache-Control", "value": "max-age=604800" }
          ]
        }
      ]
    }
  ]
}
```

## GitHub Pages

GitHub Pages 由 repository 的 gh-pages branch 托管。对于新 repository，源页以初始化 Git / 配置 origin 作为部署准备；已有 Git remote 时可跳过：

```sh
git init
git remote add origin https://github.com/username/expo-gh-pages.git
```

安装 gh-pages 开发依赖：

```sh
npm install --save-dev gh-pages
yarn add -D gh-pages
pnpm add -D gh-pages
bun add -D gh-pages
```

repository 部署到子路径时，将 app config experiments.baseUrl 设成 repository path，例如：

```json
{
  "expo": {
    "experiments": {
      "baseUrl": "/expo-gh-pages"
    }
  }
}
```

package.json scripts 加 predeploy / deploy；--nojekyll 避免 Jekyll 忽略 Expo 导出的下划线资源：

```json
{
  "scripts": {
    "predeploy": "expo export -p web",
    "deploy": "gh-pages --nojekyll -d dist"
  }
}
```

运行 deploy 会先导出 dist，再把产物发布至 gh-pages branch。最后在 GitHub Pages 设置中将 Source 选择为 Deploy from a branch，Branch 选择 gh-pages 根目录。后续每次运行 deploy 都会触发更新。

## 关键名词

- **Output target**：静态导出策略，决定 single SPA、server 或每路由静态页面。
- **dist**：Expo Web production export 的默认静态文件目录。
- **SPA fallback**：单页应用刷新深层 URL 时，把请求改写到 index.html 后由客户端 router 处理。
- **Static rendering**：对每个已知 route 预生成 HTML，便于 crawler 读取和 CDN 缓存。
- **Redirect / rewrite**：托管服务器将请求路径路由到目标文件的规则。
- **Cache-Control**：告诉浏览器 / CDN 何时复用静态资源或重新请求 HTML 的响应 header。
- **baseUrl**：应用部署到 repository subpath 时，给资源 URL 增加的前缀。
- **SSL / HTTPS**：浏览器安全上下文；很多权限 API 在普通 HTTP 页面上不可用。
