## 两条增加原生能力的路

Expo 项目可以安装带 native code 的已有 React Native library，也可以自己写 Swift / Kotlin module。大多数 app 先尝试 SDK 模块或已有兼容库；只有库无法满足平台 API / 性能 / 集成需求时才写自己的原生代码。

### 安装含原生代码的库

Expo Go binary 只带一组预编译模块，不能动态装任意 Swift / Kotlin 代码。需要 custom native library 时，要在自己的 Development Build 中编译：

```sh
# 按当前 Expo SDK 安装兼容库版本
npx expo install react-native-localize

# 为项目本机生成 Android / iOS build
npx expo run:ios
```

如果库提供 Config Plugin，可在 app config 填权限文案 / 原生设置并再次生成工程；没有 plugin 的库可按其 README 手动改原生工程，或为 CNG 写本地 plugin。

### 编写原生模块

Expo Modules API 让 JS app 通过统一模块定义与原生 Swift / Kotlin 代码交互，也支持把原生 View 暴露成 React component。

- 仅一个 app 使用的模块，适合 **Local Expo Module**：源码放在 app 的 `modules/`，不发布到 npm，并自动接入当前工程。
- 多个 app / 消费者共享时，创建 standalone module package，可放 monorepo 或发布到 npm。
- 若主要写 C++，再查看 React Native Turbo Modules API；学习和维护模型不同。

创建本地 module：

```sh
npx create-expo-module@latest --local
npx expo run
```

若目标是共享 npm package，省略 `--local`：

```sh
npx create-expo-module@latest
```

模板会生成 Swift 与 Kotlin 的初始 module；在 CNG 项目中，新增 native dependency 后需 Prebuild / rebuild 才会进入设备 binary。

## CNG 工程注意事项

- 需要 Xcode / Android Studio 原生调试时，可以在本地 Prebuild 并用 `npx expo run` 生成开发 binary。
- 若使用 CNG，不要只修改生成目录并期待改动永久保留；app config 能表达的设置放 app config，复杂变更封装为 Config Plugin。
- 生命周期事件更适合 Expo Modules lifecycle subscriber；把代码用 Config Plugin 插到 `AppDelegate` / `MainApplication` 容易与别的插件冲突。
- Development Build 才含项目自己的 native code；新增原生依赖或原生 config 变化后必须重建，JS Fast Refresh 不会替换原生 binary。

## 关键名词

- **Native code**：直接在 iOS Swift / Objective-C 或 Android Kotlin / Java 执行的代码。
- **Expo Modules API**：Expo 推荐用于创建原生模块与 View 的跨平台接口。
- **Local module**：只随单个 app 源码维护、不独立发布的模块。
- **Turbo Module**：React Native 新架构的原生模块接口。
- **Lifecycle subscriber**：在 app native 生命周期节点执行的回调扩展。
- **Development Build**：按当前 app 编译、含自定义原生依赖的开发客户端。
