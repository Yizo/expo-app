**官方页面：**[Authentication in Expo and React Native apps](https://docs.expo.dev/develop/authentication/)

**SDK 56 路由校对：**Expo Router 的 [SDK v56 API 参考](https://docs.expo.dev/versions/v56.0.0/sdk/router/)包含 Protected Routes；该能力从更早的 Expo SDK 版本已提供，SDK 56 可用。当前指南称其为 Router v5 引入的能力，不要把“v5”误读为 Expo SDK 版本号。v56 配套 `expo-router` 为 `~56.2.21`。

## 认证流程不只是一个登录按钮

身份验证（Authentication）要处理用户是谁、凭证如何验证、登录会话怎么保存、注销后怎么清理，还要分离公开页面和登录后的页面。可先用 `isAuthenticated = true` 这样的假状态搭好导航，确认流程后再连接真实服务端；硬编码值不能作为生产认证。

## 在导航层保护页面

通常公开页面有登录 / 注册 / 找回密码；受保护页面有主页、个人资料或业务数据。Expo Router 的 Protected Routes 可以根据会话状态决定页面是否允许通过客户端导航访问；较旧版本也可用 Redirect 实现类似效果，但需要更多路由判断。

React Navigation 也支持静态和动态认证导航结构。如果采用 Expo Router，建议按 v56 对应路由 API 配置受保护路由，并在初始会话尚未恢复时先显示加载界面，避免用户短暂看到错误页面。

**重要边界：**客户端受保护路由负责 UI 导航，不是服务端授权。服务端 API 仍必须验证会话与用户权限；不要因为某页在客户端隐藏就认为数据已受保护。

## 邮箱与密码

邮箱密码是常见方案，但要额外实现忘记密码与密码重设，避免用户失去账号后无法恢复。可以自己构建，也可以使用 Clerk、Supabase、Cognito、Firebase、Better Auth 等服务提供的认证组件 / SDK。

Expo 指南建议开发者查看 OWASP Authentication Cheat Sheet 中的密码长度、恢复流程、凭证保护等做法。指南也提醒，应用商店对社交登录和平台账号登录可能有审核要求；发版前应按当前商店规则确认组合方式。

## 无密码登录：Magic Link 或 OTP

### Magic Link

服务端给用户发邮件，用户点击链接后由系统回到 app，验证链接并建立会话。深层链接是关键：链接要能打开你的 app 并导向正确页面。Expo Router 对很多场景自动处理 linking；React Navigation 则需要显式配置。

### One-Time Passcode（OTP）

服务端发送邮件 / 短信验证码，用户复制回 app 输入。验证码有有效期，因此需要过期与重发规则。Android / iOS 有机会识别短信验证码并给键盘上方的自动填充建议。OTP 流程不依赖 deep link。

## OAuth 2.0

OAuth 2.0 让用户用 Google、Apple、GitHub 等已有账号授权，而 app 不直接处理对方账号密码。一般流程由授权服务引导用户授权并返回临时 code，app / 服务端将 code 换成访问令牌。

Expo 页面介绍了一个可自行掌控的实现：

1. Expo Router 启动登录入口与回调路由。
2. `expo-auth-session` 打开浏览器 / 原生登录界面并接收授权响应。
3. OAuth 服务把 code 回调到 Expo Router API Route。
4. API Route 在服务端安全交换授权 code、保管密钥，并可签发应用自己的 JWT。
5. Web 端可用安全 Cookie 保存会话；Android / iOS 可将敏感会话凭证保存在 `expo-secure-store`。
6. 服务端每次请求仍需验证 JWT、过期时间与授权范围。

Expo API Routes 在这里充当轻量的服务端中介，让私密 Client Secret 不进入 JS app bundle。Expo AuthSession 负责客户端启动登录界面、处理回调和把用户带回 app。

Apple / Google 也提供平台原生登录界面；需要原生体验时可查 [Sign in with Google](https://docs.expo.dev/guides/google-authentication/) 与 [`expo-apple-authentication` SDK v56 API](https://docs.expo.dev/versions/v56.0.0/sdk/apple-authentication/)（推荐版本 `~56.0.4`）。

## 现成 Auth 服务

| 服务 | Expo 指南概述 |
| --- | --- |
| Better Auth | 开源认证服务，可搭配 Expo API Routes，在应用侧保留更多控制权。 |
| Clerk | Email、密码、OTP、Magic Link、OAuth、Passkeys 等预制能力，并有 Expo 原生模块。 |
| Supabase | PostgreSQL 后端服务中的认证能力，支持多种 OAuth 及邮箱流程。 |
| Amazon Cognito | AWS 身份池与用户池，可通过 Amplify 接到 Expo；配置较多但适合 AWS 栈。 |
| Firebase Auth | Firebase 认证平台；若使用 React Native Firebase，需 Development Build，因为库含 Expo Go 未预装的原生代码。 |

## 生物识别与 Passkey

- **Biometrics（生物识别）**：Face ID / Touch ID 可以在本地解锁已有会话或凭证；单独弹出指纹 / 面容框并不能代替服务端验证。
- **Passkeys**：基于公私钥的无密码登录方式，可由平台安全能力保护；注册 Passkey 通常应在用户已有会话后进行。Expo 文档列出 `react-native-passkeys` 和 Clerk Passkeys 作为集成方向。

## 推荐的迭代顺序

先选适合产品的最小认证方案，例如邮箱 OTP 或 Magic Link，确认会话恢复和受保护路由后再增加 OAuth、设备信任、生物识别或 Passkey。这样容易验证链接回调、token 存储和跨平台行为。

## 关键名词

- **Session / 会话**：认证成功后用于持续识别用户的一段状态 / 凭据。
- **Authorization Code**：OAuth 流程中短时有效的中间 code，通常由服务端交换为 token。
- **JWT**：服务端签发的带签名 Token；服务端必须校验签名、过期时间和授权内容。
- **Deep Link**：外部链接回到 app 内特定页面的地址机制。
- **Magic Link**：通过一次性邮件链接完成认证的密码无关流程。
- **OTP**：限时有效的一次性验证码。
- **Protected Route**：根据当前会话控制客户端页面访问的路由；它不取代 API 的服务端授权检查。
